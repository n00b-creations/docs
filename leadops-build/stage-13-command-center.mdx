# Stage 13 — Visual LeadOps Command Center

Stage 13 turns the LeadOps platform into a unified operational console. The objective is not another dashboard layered on top of the system; it is the primary operator interface for the intelligence, revenue, control-plane, integration, workflow, agent, approval, and audit capabilities built in Stages 6–12.

## 1. Stage Objective

The Command Center consolidates:

- Lead and opportunity intelligence
- Revenue and funnel performance
- Autonomous agents and agent tasks
- Workflow definitions and live executions
- Integration health and synchronization
- Human approvals
- Policy decisions and blocks
- Real-time events
- Audit history
- Search, command, and drill-down workflows

The core interaction model is:

```text
USER
  ↓
COMMAND CENTER
  ├── Search / Command
  ├── Workspace
  ├── Queue / Pipeline
  ├── Intelligence
  ├── Automation
  ├── Revenue
  ├── Integrations
  ├── Agent Operations
  └── Audit / Administration
          ↓
     API / BFF
          ↓
  LeadOps Control Plane
          ↓
 Intelligence • Workflows • Agents • Integrations • Revenue
```

The server remains authoritative. The browser is an operational view and command surface, not a second source of truth.

## 11. Real-Time Event Architecture

The Command Center should receive operational updates through a dedicated realtime gateway.

```text
Domain Events
     ↓
Event Bus
     ↓
Realtime Gateway
     ↓
WebSocket / SSE
     ↓
Browser Event Store
     ↓
Workspace Selectors
     ↓
UI
```

Recommended event envelope:

```ts
interface CommandCenterEvent {
  id: string;
  tenantId: string;
  sequence: number;
  type: string;
  entityType: string;
  entityId: string;
  occurredAt: string;
  version: number;
  source: string;
  payload: unknown;
}
```

Required behavior:

- Sequence numbers
- Cursor-based recovery
- Heartbeats
- Reconnection
- Backoff
- Duplicate detection
- Event versioning
- Tenant filtering
- Permission filtering

The browser should never assume that an event represents final authoritative state. For critical mutations, refetch the authoritative resource after the event.

## 12. Frontend State Model

Separate state into three classes.

### Server State

Examples:

- Leads
- Opportunities
- Workflows
- Agents
- Integrations
- Approvals
- Revenue metrics

Server state is cached but authoritative data comes from APIs.

### UI State

Examples:

- Selected workspace
- Open drawer
- Filters
- Sort order
- Layout
- Theme
- Density

### Ephemeral State

Examples:

- Hover
- Drag position
- Temporary form state
- Command palette query
- Connection animation

This separation prevents transient UI behavior from contaminating domain state.

## 16. Security Model

The Command Center must enforce security at the API boundary and reflect permissions in the UI.

```text
UI Permission Check
       ↓
BFF Authorization
       ↓
Control Plane Policy
       ↓
Tenant Authorization
       ↓
Capability Scope
       ↓
Execution
       ↓
Audit
```

Hiding a button is not authorization.

Every mutation must be re-authorized server-side.

Sensitive information should be masked in:

- Lead contact data
- Credentials
- API tokens
- Provider responses
- Communication content
- Agent inputs/outputs
- Audit metadata

## 18. Performance Strategy

Large tenant datasets must not be rendered wholesale.

Required patterns:

- Cursor pagination
- Virtualized tables
- Server-side filtering
- Server-side sorting
- Incremental event ingestion
- Lazy-loaded workspaces
- Memoized selectors
- Query caching
- Batched requests
- Debounced search
- Background refresh
- Stale-while-revalidate where safe

The realtime layer should update affected records rather than forcing complete dashboard reloads.

## 19. Acceptance Tests

Stage 13 is complete when:

### Navigation

- Role-specific navigation is enforced.
- Unauthorized workspaces cannot be accessed directly.
- Deep links resolve correctly.
- Saved views persist.

### Data

- Server state is authoritative.
- Filters are tenant-scoped.
- Large tables use pagination/virtualization.
- Stale data is visibly identifiable when relevant.

### Realtime

- Connections reconnect automatically.
- Duplicate events do not duplicate UI state.
- Sequence gaps trigger cursor recovery.
- Events are tenant- and permission-filtered.

### Workflows

- Execution timelines show node-level state.
- Failed nodes expose actionable diagnostics.
- Approval states update in real time.
- Policy blocks remain visible.

### Agents

- Agent health is visible.
- Tasks can be inspected according to permissions.
- Retry/dead-letter state is visible.
- No hidden model reasoning is surfaced.

### Integrations

- Connector health is visible.
- Sync lag is visible.
- Provider failures are isolated.
- Credential values never appear in UI payloads.

### Security

- Every mutation is server-authorized.
- Tenant isolation is tested.
- Sensitive fields are redacted.
- Audit events are generated for privileged actions.

### Accessibility

- Keyboard navigation works across primary workflows.
- Dialogs and drawers are accessible.
- Focus management is correct.
- Reduced-motion mode works.
