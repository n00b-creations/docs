# Stage 12 — Integration Marketplace & Workflow Automation

Stage 12 turns the connector layer from Stage 11 into a visual, extensible automation system. Users can install integrations, map data, define triggers, compose actions, invoke agents, enforce policies, and observe every execution without coupling the core LeadOps domain to a specific provider.

## Connector marketplace

Each connector is represented by a versioned manifest.

```ts
export interface ConnectorManifest {
  id: string;
  name: string;
  version: string;

  category:
    | "crm"
    | "marketing"
    | "communications"
    | "calendar"
    | "payments"
    | "analytics"
    | "enrichment";

  capabilities: string[];
  requiredScopes: string[];

  supports: {
    inboundEvents: boolean;
    outboundActions: boolean;
    synchronization: boolean;
  };
}
```

The marketplace must validate the manifest before installation.

## Workflow compiler

The visual workflow should not execute directly from UI state.

Use:

```
Visual Definition
      ↓
Schema Validation
      ↓
Graph Validation
      ↓
Permission Validation
      ↓
Dependency Validation
      ↓
Policy Validation
      ↓
Compiled Workflow
      ↓
Runtime
```

The compiler should reject:

- Cycles that are not explicitly bounded
- Missing trigger nodes
- Unreachable required nodes
- Invalid connector capabilities
- Missing permissions
- Unsupported provider operations
- Unbounded loops
- Missing policy profiles
- Invalid field mappings

## Field mapping engine

Providers use different schemas. The mapping layer translates them into canonical LeadOps fields.

```text
Provider Field
      ↓
Mapping Rule
      ↓
Transformer
      ↓
Validation
      ↓
Canonical Field
```

Example:

```yaml
mapping:
  source: crm.contact.mobilePhone
  destination: lead.phone
  transform: normalizeE164
  required: false
```

Transformers should be deterministic and testable.

## Workflow runtime

```ts
interface ExecutionContext {
```

The runtime records each node execution.


## Autonomous agent integration

Agents become workflow nodes rather than uncontrolled background processes.

```
Workflow
   ↓

   ↓

   ↓
Control Plane
   ↓

   ↓

   ↓
```

This preserves Stage 9's rule that the control plane owns permissions, task state, and policy.

## Safety boundaries

The workflow engine must not become a mechanism for bypassing platform safeguards.

Required controls:

- Consent checks
- Suppression checks
- Tenant authorization
- Connector permissions
- Frequency limits
- Rate limits
- Approval policies
- Idempotency
- Audit logging
- Kill switches
- Workflow versioning
- Explicit bounded loops
- Provider failure isolation

## Stage 12 acceptance criteria

- Connectors can be installed and managed through the marketplace.
- Connector capabilities are discoverable.
- Workflow definitions are versioned.
- Visual workflows compile into validated executable graphs.
- Invalid graphs cannot be published.
- Field mappings are validated before execution.
- Agent actions execute through the control plane.
- High-impact actions can require human approval.
- Workflow executions are idempotent.
- Retries are bounded and observable.
- Every execution has an audit trail.
- Tenant isolation is preserved.
- Connector failures do not corrupt authoritative LeadOps state.
- Published workflows can be paused or disabled.
- Workflow execution can be inspected node-by-node.
