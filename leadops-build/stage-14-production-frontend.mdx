# Stage 14 — Production Frontend Implementation & Design System

Stage 14 converts the Stage 13 Command Center architecture into a production frontend implementation plan. The objective is to establish the actual application shell, routing, component system, server-state integration, realtime client, workspace surfaces, accessibility foundation, and test strategy.

## 1. Implementation Objective

The frontend is organized as a thin operational client over the LeadOps BFF and control plane.

```text
Browser
  ↓
Web Application
  ├── App Shell
  ├── Workspace Router
  ├── Design System
  ├── Server State
  ├── Realtime Client
  └── Feature Modules
          ↓
       BFF/API
          ↓
   LeadOps Control Plane
          ↓
 Intelligence / Revenue / Workflow / Agent / Integration Services
```

The frontend does not implement authorization, policy, workflow execution, or business-critical state transitions locally.

---

## 2. Recommended Frontend Stack

The implementation should use a typed React/TypeScript application with:

- React
- TypeScript
- App-router capable routing
- Server-state query/cache layer
- Schema validation at API boundaries
- Accessible component primitives
- WebSocket/SSE realtime transport
- E2E browser testing
- Unit/component testing
- Strict TypeScript configuration

The exact framework can remain replaceable. Domain features should not depend directly on framework-specific APIs.

## 4. Application Shell

The first implementation milestone is the shell because every workspace depends on it.

Required shell components:

```text
<AppShell>
  <GlobalHeader />
  <WorkspaceNavigation />
  <CommandBar />
  <WorkspaceViewport>
    <WorkspaceToolbar />
    <WorkspaceContent />
    <ContextDrawer />
  </WorkspaceViewport>
  <SystemStatusBar />
</AppShell>
```

The shell owns:

- Authentication state
- Current tenant
- Current workspace
- Navigation permissions
- Global search
- Command palette
- Notifications
- Approval count
- Connection status
- User preferences

It should not own domain business logic.

---

## 5. Workspace Routing

Use URL-addressable routes so operational state can be shared and bookmarked.

Example:

```text
/command-center
/leads
/leads/:leadId
/opportunities
/opportunities/:opportunityId
/workflows
/workflows/:workflowId
/workflows/:workflowId/executions/:executionId
/agents
/agents/:agentId
/approvals
/integrations
/integrations/:integrationId
/revenue
/admin/audit
```

Filters should be serializable where practical:

```text
/leads?status=qualified&owner=me&sort=score_desc
```

Deep links must reproduce the same authorized view without depending on client-local memory.

- Dark

## 8. API Client

All BFF calls should pass through a typed API client.

Example contract:

```ts
interface ApiClient {
  get<T>(path: string, options?: RequestOptions): Promise<T>;
  post<T>(path: string, body?: unknown): Promise<T>;
  put<T>(path: string, body?: unknown): Promise<T>;
  delete<T>(path: string): Promise<T>;
}
```

API responses should be validated at the boundary.

```text
HTTP response
    ↓
Schema validation
    ↓
Canonical frontend type
    ↓
Server-state cache
    ↓
Feature component
```

A malformed response should produce a controlled error rather than silently corrupting UI state.

---

## 9. Server State

Domain records should live in the server-state layer.

Examples:

- leads
- opportunities
- workflows
- workflow executions
- agents
- approvals
- integrations
- revenue summaries

Required behaviors:

- Cache
- Deduplication
- Refetch
- Invalidations
- Pagination
- Optimistic updates only where safe
- Error recovery
- Loading states
- Stale-state indicators

Mutations that have policy or financial consequences must use server-authoritative responses rather than assuming the requested state change succeeded.

## 10. Realtime Client

Implement a reusable realtime transport.

```ts
interface RealtimeClient {
  connect(): Promise<void>;
  disconnect(): void;
  subscribe(filter: EventSubscription): Unsubscribe;
  acknowledge(sequence: number): void;
  recover(cursor: string): Promise<void>;
}
```

Event processing:

```text
CONNECT
  ↓
AUTHENTICATE
  ↓
SUBSCRIBE
  ↓
RECEIVE EVENT
  ↓
CHECK TENANT / PERMISSION
  ↓
CHECK SEQUENCE
  ├── expected → APPLY
  ├── duplicate → IGNORE
  └── gap → RECOVER
  ↓
INVALIDATE / PATCH CACHE
  ↓
RENDER
```

The event stream must not directly mutate arbitrary React component state.

## 16. Approval Center Implementation

Approval cards should make the proposed action understandable without exposing unnecessary internal reasoning.

Display:

- What will happen
- Which entity is affected
- Which workflow/agent requested it
- Applicable policy
- Risk category
- Expiration
- Available decisions

Approval mutation flow:

```APPROVE / REJECT
       ↓
BFF
       ↓
AUTHORIZATION
       ↓
CONTROL PLANE
       ↓
POLICY RECHECK
       ↓
STATE TRANSITION
       ↓
AUDIT EVENT
       ↓
REALTIME UPDATE
```

The policy must be rechecked because conditions may have changed since the approval was displayed.

## 19. Error and Loading Architecture

Every workspace needs explicit:

- Loading state
- Empty state
- Permission denied state
- Not found state
- Validation error
- API failure
- Realtime disconnected state
- Stale data state

Do not render a blank panel when a request fails.

Example:

```text
REALTIME DISCONNECTED
Last synchronized: 06:24:17
[Reconnect]
```

The UI should remain useful when realtime is unavailable by falling back to normal API refresh.

## 22. Performance Budgets

Establish measurable frontend budgets.

Track:

- Initial route load
- JavaScript payload
- Largest contentful paint
- Interaction latency
- Search response latency
- Table render time
- Realtime event processing time
- Memory growth during long sessions

Large datasets must use virtualization or pagination.

Avoid rendering complete histories when only the visible range is needed.

---

## 24. Security Acceptance Tests

The frontend implementation is not complete until these scenarios are covered:

- Unauthorized route access is rejected.
- Unauthorized actions cannot be invoked through direct API calls.
- Tenant A data never appears in Tenant B queries.
- Credentials never appear in browser-rendered payloads.
- Sensitive fields are redacted.
- Approval actions are re-authorized.
- Policy-sensitive actions cannot bypass the control plane.
- Expired sessions are handled cleanly.
- Realtime events are tenant-scoped.
- Audit events are generated for privileged actions.

## 26. Definition of Done

Stage 14 is complete when the LeadOps frontend is no longer a conceptual dashboard.

It must provide:

- Real route-addressable workspaces
- Shared production design system
- Typed API integration
- Authoritative server state
- Realtime event handling
- Lead 360
- Pipeline
- Workflow execution inspection
- Agent operations
- Approval management
- Integration health
- Revenue views
- Search and command palette
- Permission-aware navigation
- Accessibility coverage
- E2E coverage
- CI quality gates
- Production build verification

The frontend remains deliberately separated from the execution authority:

```text
FRONTEND
  ↓
BFF
  ↓
CONTROL PLANE
  ↓
POLICY
  ↓
EXECUTION
  ↓
AUDIT
```

This boundary prevents the browser from becoming an unauthorized execution engine.
